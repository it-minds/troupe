// 01 · WHAT IS INSIDE WHAT

Four layers

The model thinks; everything around it is ours. An LLM sits inside an agent, which is a role. The agent sits inside the harness, which runs it: a workspace, tools, approvals, and a log of everything that happened. The harness sits inside a client — a terminal, the desktop app, or a program you wrote — which talks to it over one protocol.

The line that matters is the harness's edge. Anything a client can do goes through the protocol, and there is no private back door for our own apps: what the console does, a script can do. Swap the model, swap the client, and the harness is the same.

// 02 · THE SAME HARNESS, TWO HOMES

Where the work runs

One harness, whether it runs on your laptop or in a pod. On a laptop it is the daemon; on the cluster it is a worker. Three clients — the terminal, the desktop app, the web console — speak the same protocol to either, so a session feels the same wherever it lives.

What an agent may call is a short list: read and write files, run a shell, search, delegate, remember. Some of those ask first. Which ones ask is not the model's choice and not the agent's; it is the person's rules, or the organisation's, and the harness enforces them before the call runs.

// 03 · ASK ONCE, THEN TALK DIRECTLY

The plane and the pods

The plane is the front door, not the middleman. A client asks the plane for a session on a profile; the operator keeps pods running per profile; the plane hands the client a pod to talk to directly. From then on the conversation is between the client and its pod, with the plane keeping the index, the audit and the keys.

The daemon at home is the same picture with the plane left out: a laptop runs its own harness and needs nobody's permission to start. Five images make up a deployment: the plane, the operator, the worker, the console and the a2a gateway.

// 04 · FOUR SOCKETS

Bring your own

The harness is a puzzle piece with four sockets: which client drives it, which model thinks, which tools it may use, and where it runs. Each socket takes more than one piece. Anthropic or a gateway of your own in the model socket; your own MCP servers in the tools socket; a laptop or a cluster in the last.

Nothing in the harness assumes a particular answer to any of the four. That is what makes it fit an organisation that already has opinions about models, tools and where code may run.

// 05 · THE NOUNS

Actors, sessions, profiles

Three nouns carry the whole system. An actor is whoever acts: a person, a service principal, or an agent acting for one of them, and every event names its actor. A session is a log: an append-only record of turns, calls, approvals and results, which the harness can replay to the same state. A profile is what a team is held to: the model, the tools, the limits, the image, the budget.

Because a session is its log, it can go dormant and wake, move between pods, be audited line by line, or be erased by destroying its key. Because a profile is one thing, an organisation can say in one place what a team's agents may do.

// 06 · THINK, ACT, REPEAT

One turn

A turn is one input and everything the agent does with it. The model streams its thinking and its text as deltas; it asks for tools; the harness runs them, several at once where it can, and feeds the results back; the loop continues until the agent finishes or hits a limit. The next input is the next turn.

Approval gates sit inside the loop, not around it. A call that needs a yes waits for one — from the person at the keyboard, from someone steering remotely, or from a rule — and the rest of the turn waits with it. Every delta, call and answer is a line in the log, which is why a client that attaches late sees exactly what one that was there saw.

// 07 · WHAT RUNS WHERE

On the cluster

One system namespace, and one namespace per profile. The plane, the operator, the console and OpenBao live in the system namespace. Each profile's workers live in a namespace of their own, with the Secrets they need copied in by the operator, a Pod Security level the pod actually needs, and a network policy that admits the plane's control channel and the egress the profile names, and nothing else.

Two ingresses: one for people and clients, one for the a2a gateway. The control channel between the plane and a pod is internal and encrypted; what a pod may reach outside is a short list of hosts, and the cloud's metadata service is never on it.

// 08 · THREE JOBS FOR ONE KEY MANAGER

Keys, and erasure

OpenBao does three things, and the plane never holds a raw key. It signs the plane's tokens and the plane's word to clients, so a client can pin the plane's public key and refuse a forged policy. It holds one key slot per session on a pod, so a session's log at rest is readable only through that slot. And it holds a person's own slots, for what is theirs alone.

Erasure is destroying the key first. A session whose key is gone is unreadable wherever its bytes still sit: in the object store, in a backup, in a pod that has not been drained yet. The rows go after; the proof that nobody can read them comes first.

// 09 · WORK NOBODY STARTS

Triggers

A trigger is a frozen request. A schedule, a webhook from a repository, or another agent fires it; what fires is a revision — the profile, the agent, the prompt and the terms, hashed, so the run is exactly what an administrator approved and not what the file says today.

The session runs as a service principal with its own terms: how many turns, which approvals are denied outright, how many at once. It is flagged for review until a person looks, and a run nobody looked at cannot be mistaken for one somebody did. A blind retry within a minute is the run it repeats, never a second one.

// 10 · SIX HABITS

Habits of the harness

Six things the harness does without being asked, because an agent that does them badly is worse than no agent.

  • Worktrees: a session works in a worktree of its own, never on a branch someone else has checked out.
  • The project brief: a repository's own instructions reach every session in it — once the workspace is trusted, and never a program it carries.
  • Watch mode: the harness notices what changed on disk, so the agent reads what is there and not what it remembers.
  • Bounded results: a tool's output is cut at a size the model can use, with a way to read the rest on purpose.
  • Replay from the log: a crash, a move or a wake rebuilds the session from its own record.
  • Goal and loop: a turn knows what it is for, and ends when it is done or when a limit says so.
// 11 · WHY ERLANG

Why the BEAM

A session is a supervision tree, and the failure rules are drawn, not written. The root agent, its delegates, its tool calls and its link to the client are processes under supervisors with stated restart rules: a tool that crashes takes nothing else with it; a root that dies is restarted from the log; a client that drops leaves the session running.

The ledger on the right is the honest version of the argument. What the BEAM gives for free — isolation, supervision, cheap concurrency, hot introspection, distribution between replicas — is what you would write by hand, and get subtly wrong, in Rust or Go. The cost is a runtime fewer people know. We take that trade for a system whose job is to keep going while things fail.

// 12 · SCALING FROM DEMAND

It breathes

Pods follow demand, and the plane is the only one who counts. Every fifteen seconds the plane looks at the sessions each profile has and the pods it has, decides how many it wants, and writes that number into the WorkerProfile. The operator reconciles a StatefulSet to it. Pods heartbeat back, so the plane knows which are alive and which are still finishing something.

Scaling down drains the highest ordinal first: the plane tells the pod, the pod puts its sessions to sleep one by one and reports progress, the plane waits while progress is made, and the operator replaces the pod the moment the plane records it drained. A quiet profile goes to zero over a night and comes back with the first session in the morning.

// 13 · WHO IS CALLING

Whose identity

When a pod calls a tool, the question is whose name it speaks in. A shared session makes it sharp: one person's tool can be driven by the others at the table. Three answers were on the table — the system's identity only; on behalf of a person, with a token minted for them; or client-hosted, where the tool stays on the person's laptop and the call is relayed back over their own socket.

Troupe took the third for personal tools: a person's signed-in servers are offered to a session with consent, the token never leaves their machine, and every participant sees a line saying whose tools the session is using. System identities stay for what a profile owns. This picture is the one to argue from when the question comes up again.

// 14 · WHERE CONFIGURATION LIVES

A profile is the config

Configuration is a ladder, and the profile is the rung an organisation holds. Defaults, then the person's own file, then the repository's, then the environment; above them, on a pod, the profile: a versioned, hashed bundle of agents, servers, skills and limits, under a policy ceiling nobody below it can raise.

The pod enforces it and the session remembers which revision it ran under, so an audit can say what rules applied to a turn months later. The alternative on the right — config on every laptop, hand-edited, drifting — is what most teams have today, and why a profile is worth the ceremony.

// 15 · A ROLE IN A FILE

An agent is a file

An agent is a markdown file: a frontmatter contract and a prose role. The frontmatter says what it may use — the model, the tools, delegation, limits; the prose says who it is. It can live in four layers, lowest to highest: built in, the person's own, the repository's, the profile's bundle, and the highest that names it wins.

A session has one root agent, which may delegate to others and branch its own work. The same session.create starts it whether a person asked or a trigger fired; on a pod the agent is read from the pinned bundle, so what runs is what was published, not what someone has on disk.

// 16 · TOOLS, AND WHOSE THEY ARE

MCP tools

MCP in one breath: a server lists tools, a client calls them, the answers come back as text. One pod session's tool list holds three kinds at once: the harness's built-ins, the servers the profile's bundle names, and the tools on your own laptop.

The last kind is the point. You attach, you are asked whether to offer your servers, you choose which; the session discovers them; a call to one of yours is sent back over your own socket and runs on your machine with your sign-in. The rules: the token never leaves the laptop, every participant sees whose tools are in play, the tools leave with you, and a profile can forbid it outright.
