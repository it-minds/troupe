# The A2A facade

Other agents and platforms — LiteLLM's A2A gateway among them — delegate a task to a
worker profile and get a result, without learning anything about sessions, pods or the
human protocol. Each profile is a callable capability with a published agent card.

The facade is a client. It uses the same public APIs as the TUI and the GUI, holds no
credential the plane does not mint for it, and cannot read a session it is not on the
access list of. That is what keeps it an afternoon's deployment rather than a hole in
the wall.

---

## Brings, takes, already in place

**Brings.** A profile becomes something another agent can call: "send this to the
`reviewer` agent and give me back its findings". The studio's own LiteLLM gateway can
route to it. The mapping is small because the event model was designed for it.

**Takes.** One new deployable, `troupe_a2a`, that speaks the A2A protocol on one side
and the plane API plus the worker WebSocket on the other; a per-profile agent card
generated from the bundle; a principal per calling party; a status the plane can answer
without a reader; and a decision about artifacts.

**Already in place.**

* A task is a session, a message is an input, and every effect is a durable event
  with a sequence number and a hash, so a task's history is exact and replayable
  (`PROTOCOL.md` §4, §6).
* `input-required` is an approval: `approval_requested` waits durably and
  `approval.respond` resumes the turn, days later if need be.
* Artifacts have a model: the `publish` tool writes to a team volume and logs
  `published {source, destination, hash, bytes}`; blobs and files are readable over
  `blob.get` and `fs.read` (`apps/troupe_core/lib/troupe/tools/publish.ex`).
* Sessions move between pods behind the client's back, and nothing in the protocol
  assumes they do not — fencing by epoch was built for that.
* Service principals and `prompt` through activation come from the triggers plan; the
  facade is their second user.

## What is missing today, precisely

| Gap | Where |
| --- | --- |
| No non-human caller at `/rpc`; no per-profile discovery document. `/.well-known/troupe` describes the plane, `profiles.list` returns pods and capacity, not capabilities. | `router.ex:47-61`, `harness.ex:83-100` |
| A finished task's status cannot be read from the plane: `sessions.list` has no status or done reason, and reading the log needs a reader pod. | `harness.ex:296-316`, `apps/troupe_worker/lib/troupe/worker/session/reader.ex` |
| Nothing produces "the answer" as a value. The final assistant text is the last `llm_response` in the log; there is no summary the facade could hand back without replaying. | `apps/troupe_core/lib/troupe/agent/server.ex:1412` (`agent_done` carries `summary` only when the agent called `finish`) |
| No outbound HTTP from the plane; push notifications would be the first, and egress is allowlisted. | `spec.md:118` |

## Design

### 1. Where the facade lives

`apps/troupe_a2a`: a Plug application in the umbrella, depending on `troupe_protocol`
only (the boundaries task enforces it, as it does for the TUI), built as a fourth
server image and deployed in `troupe-system` behind the same ingress at
`a2a.<domain>`. It is a client of the plane and of workers; it has no database. What
it must remember between requests — which A2A task maps to which session and caller —
is the session row itself: the plane records `origin: {"kind": "a2a", "caller":
"<principal>", "task": "<id>"}` at create, and the facade recovers everything from
`sessions.list(origin: a2a)` after a restart. Two replicas are fine; nothing is
serialised in the facade.

### 2. Who is calling

An A2A caller authenticates to the facade with a bearer token from the identity
provider (client credentials) or, for the small release, a plane service principal's
secret. Either way the facade exchanges it at `/auth/exchange` and acts as that
principal: one principal per calling party, owned by a team, granted the profiles it
may call. LiteLLM's A2A gateway is one caller with one principal. There is no
"anonymous" and there is no facade-wide credential that can reach every profile: a
compromised facade holds nothing more than each caller's own short-lived plane token.

### 3. Agent cards

`GET /a2a/<profile>/.well-known/agent-card.json`, generated by the facade from
`profiles.list` (which, from the skills plan, returns the bundle's primaries, skills
and MCP servers):

```json
{"name": "reviewer", "description": "Reviews a change against the IT Minds checklist…",
 "url": "https://a2a.example.com/a2a/reviewer",
 "version": "bundle:stable/7",
 "capabilities": {"streaming": true, "pushNotifications": false, "stateTransitionHistory": true},
 "authentication": {"schemes": ["Bearer"]},
 "defaultInputModes": ["text/plain", "text/markdown"],
 "defaultOutputModes": ["text/markdown", "application/octet-stream"],
 "skills": [{"id": "review-checklist", "name": "Review checklist",
             "description": "How we review a pull request at IT Minds"}]}
```

Troupe skills are A2A skills — same word, same meaning, one source. The card's version
is the bundle version, so a caller can tell when the capability changed. The card is
public; everything else needs a token.

### 4. The mapping

| A2A | Troupe |
| --- | --- |
| `message/send` with no task | `session.create {profile, prompt: <message text>, origin: a2a, visibility: private}` as the caller's principal; the task id is the session id |
| `message/send` on a task | `input.send` on the worker socket (the facade opens it with the token from `session.open activate`) |
| `message/stream` | the same, then `subscribe session:<id> detail` and translate events into A2A `status-update` and `artifact-update` events over SSE |
| `tasks/get` | the plane row's `status`, `done_reason` and the task's artifacts; with `historyLength > 0`, a reader over `session.open read` renders the last messages |
| `tasks/cancel` | `turn.cancel`, then `session.archive` |
| `input-required` | `approval_requested` — the A2A status carries a message describing the tool and its arguments; the caller's next `message/send` on that task with a structured part `{"decision": "allow"|"deny", "call_id": …}` becomes `approval.respond`; free text on a waiting task is refused with a hint, because text cannot answer a yes/no the log will record as a decision |
| task states | `submitted` (row created) → `working` (thinking/acting) → `input-required` (pending approval) → `completed` (`done` with reason `finished`) / `failed` (`llm_error`, `budget_exhausted`, `interrupted`) / `canceled` |
| artifacts | see below |
| `pushNotificationConfig` | not supported in the first release; the card says so |

The final answer of a task is the text of the last root `llm_response` in the turn
that ended it, or `agent_done.summary` when the agent used `finish`. The facade returns
it as the task's `status.message`. That is a rendering of the log, done by the facade
with a reader, never stored in the plane.

### 5. Artifacts

Two kinds, both already in the log:

* **Published files.** A `published {destination: "team:acme/reviews/pr-812.md", hash,
  bytes}` event becomes an artifact with one `file` part whose `uri` is a facade URL,
  `https://a2a…/a2a/tasks/<id>/artifacts/<hash>`, which the facade serves by `fs.read`
  on the session's mounts with the caller's own token. The hash is the artifact id and
  the caller can verify what it fetched.
* **Large tool results and blobs.** A blob reference in an `llm_response` or
  `tool_call_completed` becomes a `file` part served from `blob.get` the same way.

Text answers are `text` parts; structured tool results the model returned as JSON are
`data` parts. The facade invents nothing: an artifact exists because an event says so,
and it is fetched through the session's own access checks.

### 6. Costs and limits, stated

* **Reading a finished task costs a reader pod.** The plane cannot decrypt a session
  and structurally never will; `tasks/get` for history or an artifact fetch opens a
  reader on a pod of the profile, cheap but not free, and fails with `unavailable` when
  the profile has no healthy pod. The facade caches nothing across calls, so a caller
  that polls history in a loop pays for it; the card advertises `stateTransitionHistory`
  and `tasks/get` without history is answered from the plane row alone.
* **Streaming is a socket per active stream**, held by the facade to the pod. A stream
  that outlives the pod token is refreshed with `token.mint` and `auth.refresh`, as the
  GUI does.
* **Concurrency and budget** are the caller's principal's terms: `terms` on
  `session.create` from the trigger plan, set per principal by the team admin.
* **No push notifications** in the first release: they would be the plane's or the
  facade's first outbound call through an egress policy that names LLM endpoints and git
  hosts. When needed, they are the facade's, to an allowlist the admin edits, never the
  plane's.

### 7. What the facade cannot do, on purpose

It cannot see a session its principal does not own or sit on the ACL of; it cannot
grant itself access; it cannot approve on the caller's behalf without a decision the
caller sent; it cannot read a team volume outside the session's mounts. All of those
are the existing checks, exercised through the existing protocol, by one more client.

## Data model

Nothing new in the plane beyond what the triggers plan adds: `origin` on the session
row carries `kind: a2a`, `caller` and `task`. The facade holds no state.

Protocol: no worker changes. Plane: `profiles.list` detail (skills plan) and the status
columns (triggers plan) are reused.

## Order of work

1. `troupe_a2a` skeleton: card generation from `profiles.list`, bearer exchange, the
   boundaries rule.
2. `message/send` and `tasks/get` without history: create, input, status from the row.
3. `message/stream`: the socket, the event translation, token refresh.
4. `input-required` both ways.
5. Artifacts: `published` and blobs as file parts; the artifact route.
6. `tasks/cancel`, history rendering, the conformance run against LiteLLM's A2A client.

## Done items, proven by command output

* `curl` the card for `reviewer`; it lists the bundle's skills and version.
* LiteLLM's A2A gateway, configured with the card URL and a principal's credential,
  routes a task to `reviewer`; the session appears in `sessions.list` with
  `origin.kind: a2a`; `tasks/get` returns `completed` with the review text.
* A task whose agent asks to run `shell` reports `input-required`; a `message/send`
  with `{"decision": "allow"}` continues it; a free-text message on the waiting task is
  refused with a hint and no `approval.respond` is logged.
* A task that publishes a file returns an artifact whose URI serves the bytes, and
  whose hash matches the `published` event.
* A second principal calling `tasks/get` on the first principal's task gets `not
  found`.
* Killing the facade mid-stream and restarting it: `tasks/get` still answers, from the
  plane row; the stream reconnects from the last `seq` the caller saw.

## Open questions

* **Who owns A2A-created sessions in the review queue?** They are the principal's
  team's; recommendation is `visibility: private` by default with the team admin able
  to set a principal's default to `team`, so a human can audit what other agents asked
  the studio's agents to do.
* **LiteLLM gateway's expectations.** The mapping above follows the A2A spec as of
  mid-2026; the conformance run in step 6 is where any gap with LiteLLM's client shows,
  and the facade should be adjusted rather than the protocol.
